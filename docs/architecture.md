# Win Activity Monitor — Architecture

**Document version:** 0.1  
**Project version:** 0.1.0  
**Status:** Draft

## 1. Purpose

This document describes the initial architecture of Win Activity Monitor.

Version 0.1 focuses on collecting Windows process creation events generated by Sysmon, transforming them into an application-specific data model, and persisting them locally.

## 2. Architectural Goals

The architecture should:

- separate Windows-specific code from platform-independent application logic
- allow core components to be tested on Linux and Windows
- isolate telemetry acquisition from event parsing and persistence
- support replacing or extending individual components in future releases
- provide a foundation for network, DNS, reporting, API, and mobile functionality

## 3. System Context

The initial process-monitoring data flow is:

```text
Windows Process
      ↓
Sysmon
      ↓
Windows Event Log
      ↓
PCMonitor Windows Event Source
      ↓
Process Event Parser
      ↓
Process Event Model
      ↓
Persistence Repository
      ↓
SQLite
```

## 4. Components

### 4.1 Sysmon

Sysmon is the initial telemetry provider.

Responsibilities:

- observe supported Windows operating-system activity
- generate process creation events
- publish events to Windows Event Log

Sysmon is considered an external dependency of PCMonitor.

### 4.2 Windows Event Source

The Windows Event Source is responsible for obtaining supported events from Windows Event Log.

Responsibilities:

- access the Sysmon event channel
- retrieve supported event records
- provide raw event data to the parsing layer
- isolate Windows-specific APIs from the rest of the application

This component is Windows-specific.

### 4.3 Process Event Parser

The Process Event Parser converts raw Sysmon process events into the internal application model.

Responsibilities:

- validate supported event input
- extract required fields
- normalize data
- handle optional fields
- reject or report malformed events

The parser shall not depend directly on Windows Event Log APIs or SQLite.

### 4.4 Domain Model

The domain model represents monitoring data inside the application.

The initial `ProcessEvent` model is expected to contain:

- event timestamp
- event identifier
- process identifier
- process GUID, when available
- executable path
- command line, when available
- parent process identifier, when available
- parent executable path, when available
- user information, when available

The domain model shall remain independent of the telemetry source and persistence technology.

### 4.5 Persistence Repository

The repository provides an abstraction for persistent storage.

Responsibilities:

- persist supported domain objects
- retrieve stored monitoring data when required
- hide database-specific operations from business logic
- support duplicate-event handling

The initial repository implementation will use SQLite.

### 4.6 SQLite Database

SQLite is the initial local persistence technology.

Responsibilities:

- provide durable local event storage
- require no external database server
- support later querying and reporting

Database-specific details shall remain inside the persistence layer.

### 4.7 Collector

The Collector coordinates the monitoring pipeline.

Conceptually:

```text
event_source
    ↓
parser
    ↓
repository
```

Responsibilities:

- request or receive raw events
- pass events to the appropriate parser
- persist successfully parsed events
- handle processing errors without terminating the entire monitoring loop
- produce diagnostic information

The Collector shall not contain Windows Event Log parsing logic or direct SQL statements.

## 5. Proposed Source Structure

```text

└── pcmonitor/
    ├── __init__.py
    ├── core/
    │   ├── models.py
    │   └── exceptions.py
    ├── parsing/

    ├── persistence/
    │   └── sqlite_repository.py
    ├── windows/
    │   └── event_source.py
    └── collector/
        └── collector.py
```

## 6. Dependency Direction

Dependencies should flow toward platform-independent application concepts.

Preferred direction:

```text
Windows Event Source
        ↓
      Parser
        ↓
   Domain Model
        ↑
    Repository
```

The domain model shall not depend on:

- Sysmon
- Windows Event Log
- SQLite
- Jenkins
- reporting clients

This reduces coupling and improves testability.

## 7. Platform Separation

### Platform-independent components

The following components should be executable and testable on Linux and Windows:

- domain models
- event parsing logic using recorded or synthetic event data
- validation
- repository interfaces
- SQLite persistence
- reporting logic

### Windows-specific components

The following components require Windows:

- Sysmon installation and configuration
- Windows Event Log access
- Windows service integration
- Windows-specific integration tests
- installer tests

## 8. Testing Architecture

### Unit tests

Unit tests shall verify components independently.

Examples:

- parser converts valid raw data into `ProcessEvent`
- parser rejects malformed data
- domain validation behaves correctly

### Integration tests

Integration tests shall verify interaction between components.

Examples:

- repository creates the required database schema
- `ProcessEvent` can be persisted and retrieved
- duplicate-event handling works correctly

### End-to-End tests

Windows E2E testing will later verify the complete flow:

```text
start test process
      ↓
Sysmon event
      ↓
Windows Event Log
      ↓
PCMonitor
      ↓
SQLite
      ↓
test verification
```

## 9. Future Extensions

The architecture should allow future additions without redesigning the core application.

Potential components include:

```text
DNS Event Source
Network Event Source
Browser Extension Source
Reporting Service
REST API
Android Client
Remote Notification Service
```

Future telemetry sources should produce application domain models rather than expose source-specific structures to the rest of the application.
