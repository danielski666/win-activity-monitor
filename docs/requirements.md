# Win Activity Monitor — Requirements

**Document version:** 0.1  
**Project version:** 0.1.0  
**Status:** Draft

## 1. Purpose

Win Activity Monitor is a Windows activity monitoring system intended to collect, process, store, and later report selected operating-system activity.

The first project milestone focuses on process creation monitoring.

## 2. Scope — v0.1 Process Monitoring MVP

Version 0.1 shall provide the minimum functionality required to collect Windows process creation events and persist them locally.

The expected data flow is:

Sysmon → Windows Event Log → PCMonitor Collector → SQLite

## 3. Out of Scope for v0.1

The following functionality is intentionally excluded from version 0.1:

- network connection monitoring
- DNS monitoring
- browser URL monitoring
- Android application
- REST API
- remote reporting
- Windows service installation
- automatic installer
- user activity time calculation

These capabilities may be introduced in future releases.

## 4. Functional Requirements

### FR-PROC-001 — Process creation collection

The system shall collect Windows process creation events generated by Sysmon.

### FR-PROC-002 — Process event parsing

The system shall extract relevant information from every supported process creation event.

The minimum required information shall include:

- event timestamp
- process identifier
- process image or executable path
- process command line, when available
- parent process information, when available
- user information, when available

### FR-PROC-003 — Event persistence

The system shall persist successfully parsed process creation events in local persistent storage.

### FR-PROC-004 — Database initialization

The system shall automatically initialize the required database structure when no existing application database is available.

### FR-PROC-005 — Invalid event handling

The system shall reject or safely handle malformed or unsupported event data without terminating the collector.

### FR-PROC-006 — Duplicate handling

The system shall provide a mechanism that prevents the same source event from being unintentionally persisted multiple times.

## 5. Non-Functional Requirements

### NFR-PORT-001 — Platform-independent core

Core business logic that does not require Windows-specific APIs shall be executable and testable on both Linux and Windows.

### NFR-WIN-001 — Windows compatibility

Windows-specific monitoring functionality shall support Windows 10.

### NFR-TEST-001 — Automated unit testing

Core application logic shall have automated unit tests.

### NFR-TEST-002 — Integration testing

Persistence and event-processing components shall be verifiable using automated integration tests.

### NFR-CI-001 — Continuous integration

Automated code-quality checks and platform-independent tests shall be executable from a CI pipeline.

### NFR-DATA-001 — Local data storage

Collected monitoring data shall remain local by default unless an explicit remote communication feature is configured in a future release.

### NFR-DATA-002 — Repository data protection

Runtime monitoring data, databases, logs, secrets, and machine-specific configuration shall not be committed to the source-code repository.

### NFR-MAINT-001 — Modular architecture

Windows-specific event acquisition shall be separated from platform-independent parsing, persistence, and business logic.

### NFR-OBS-001 — Application diagnostics

The collector shall provide diagnostic logging sufficient to identify event-processing and persistence errors.

## 6. Engineering Constraints

The initial implementation uses the following engineering constraints:

### EC-001

Python 3.11 or newer shall be used for the collector implementation.

### EC-002

Sysmon shall be used as the initial Windows telemetry source.

### EC-003

SQLite shall be used as the initial local persistence mechanism.

### EC-004

Git shall be used for source control.

### EC-005

GitHub shall be used as the remote source-code repository.

### EC-006

Jenkins shall be used as the initial CI system.

## 7. Future Scope

Potential future functionality includes:

- Sysmon network connection monitoring
- DNS query monitoring
- process-to-network correlation
- browser navigation collection
- full URL collection through browser integration
- activity-duration calculation
- reporting
- REST API
- Android client
- notifications
- multi-device support
- centralized storage
